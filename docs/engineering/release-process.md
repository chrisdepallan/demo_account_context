# Release Process

## How often does Acme Cloud release?

Each of the 12 services is released independently. Standard release windows are **Tuesday and Thursday, 09:00–15:00 US Central Time**. A service can release in every window, so the normal cadence is up to **2 releases per service per week**. Documentation-only changes can be merged at any time on a working day.

## What are the branch rules?

- `main` is the only long-lived branch. `main` is protected and always releasable.
- Work happens on short-lived branches named `<type>/<short-description>`, where the type is `feat`, `fix`, `docs`, `chore` or `hotfix`. An example is `fix/billing-retry-day-14`.
- A branch lives for at most **5 working days**. Longer work is hidden behind a feature flag and merged in parts.
- Direct pushes to `main` and force pushes to `main` are blocked.
- Pull requests are merged with a squash merge, so that each pull request is one commit on `main`.

## What are the review rules?

- Every pull request needs at least **1 approval** from an engineer on the team that owns the changed service.
- Pull requests that change the Auth, Billing or Audit Log services need **2 approvals**, and one of the approvals must come from a senior engineer of the owning team.
- A change to a service's OpenAPI description that removes or renames anything also needs an approval from Team Developer Platform.
- The author never approves the author's own pull request.
- All three continuous integration checks must pass: `tools/run_tests.py`, `tools/check_links.py` and `tools/generate_reports.py`.
- A new commit after an approval dismisses the approval.
- Reviewers respond within **1 business day**.

## How are releases versioned?

Each service uses semantic versioning, `MAJOR.MINOR.PATCH`. A release is marked with a Git tag in the form `<service>-v<version>`, for example `billing-v3.4.1`. The service changelog is regenerated by `tools/generate_reports.py` and is not edited by hand. The public API version in the URL, currently `/v2/`, is separate from the service version and changes only for breaking API changes, as described in `docs/engineering/api-design-guidelines.md`.

## What are the rollout stages?

| Stage | Where | Traffic | Minimum time before the next stage |
|-------|-------|---------|-------------------------------------|
| 1 | Staging | Test traffic only | End-to-end checks pass |
| 2 | Canary in `us-east` | **5%** | **30 minutes** |
| 3 | `us-east` | **100%** | **30 minutes** |
| 4 | `eu-central` | **100%** | **30 minutes** |
| 5 | `ap-south` | **100%** | Release complete |

The release owner watches the service's error rate and latency during every stage. The release owner is the engineer who starts the rollout and stays available until **1 hour** after stage 5.

## When is a release rolled back?

A release is rolled back at once, without discussion, when any of these conditions is true during the rollout:

- The service's HTTP 5xx rate is above **1%** for **5 minutes**.
- The service's p95 latency is more than **50%** above the value before the release for **10 minutes**.
- A SEV1 or SEV2 alert fires for the service.

The rollback uses `kubectl rollout undo` and must be complete within **15 minutes** of the decision. A fix is then prepared as a new pull request. Rolling forward under pressure is not allowed for the Auth, Billing and Audit Log services.

## How are database changes released?

Every database change is backward compatible with the previous release of the service, so that a rollback never needs a schema rollback. Schema changes follow three steps in three separate releases:

1. **Expand** – add the new column or table. Old code keeps working.
2. **Migrate** – write to both the old and the new structure, backfill, then read from the new structure.
3. **Contract** – remove the old column or table, at least **7 days** after step 2 reached all three regions.

## When are releases frozen?

- No standard release starts after **15:00 US Central Time**, on Mondays, Wednesdays or Fridays, at weekends or on US federal holidays.
- A year-end freeze runs from **20 December** to **2 January** inclusive.
- All releases of the affected service stop while a SEV1 or SEV2 incident is open for that service.

Only hotfixes are released during a freeze.

## How does a hotfix work?

A hotfix is a release outside a standard window that fixes a SEV1 or SEV2 incident or a security vulnerability.

1. Create a branch named `hotfix/<short-description>` from `main`.
2. Get **1 approval** from the owning team and the agreement of the incident commander or the team's primary on-call. Auth, Billing and Audit Log hotfixes still need **2 approvals**.
3. Continuous integration must pass. Checks are never skipped for a hotfix.
4. Roll out through the same stages, with the minimum time per stage shortened to **10 minutes**.
5. Record the hotfix in the incident record (format `INC-2026-041`).

## How are customers told about changes?

Customer-visible changes are listed in the release notes on `https://help.acme-cloud.example`. Planned maintenance that affects customers is announced on `https://status.acme-cloud.example` at least **7 days** in advance. Breaking API changes are announced at least **12 months** in advance.
